# ADR-24a · 2026-10-11 · M1 schema: RLS enforced by the database, tested with pgTAP

**Context:** Issue #24 creates `profiles`, `clients`, `measurement_sets`, `size_charts` and `admin_audit`. A user must never see another user's rows, even if the API has a bug (NFR-04).
**Decision:** (1) RLS policies and grants live in the migrations and are tested with pgTAP inside the database (`supabase test db`, `pnpm db:test`, run in the `supabase` CI job), not with Vitest. (2) `profiles.role` and `phone_verified_at` are protected by column grants (`update` only on `name` and `locale`), not by trusting the API; only the service role changes them. (3) ADR-035 follow-ups are split: the `api_app` login role (`SET` membership of `authenticated`, no inherit, no bypass) lands here, `DATABASE_URL`, the Drizzle schema mirror and the first repository land in #29; the M1 brief is corrected. Local password in `supabase/roles.sql`; the staging password is set once from a CI secret. (4) Seed accounts reuse the names in `seed-data.md` (`trial@`, `pro@`, `empty@`, `admin@`), not `user@` and `workshop@`. (5) `measurement_sets (client_id, owner_id)` is a composite foreign key to `clients (id, owner_id)`, so a set can never point at another user's client. (6) `size_charts.owner_id` null means a system chart, set means a user's private chart (Pro feature after launch, no UI yet).
**Reason:** Database rules hold for every caller; column grants make privilege escalation impossible from the client; the pgTAP matrix is the safety net.
**Alternatives:** Vitest against local Supabase (needs app code that does not exist yet); a trigger that resets `role` (hides the error instead of refusing it).
