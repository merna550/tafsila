# ADR-25a · 2026-10-11 · Auth (#25, #90, #91): locale URLs, the locale layout, runtime Supabase config and the role claim

**Context:** Issue #25 (sign-up, sign-in) was split into #90 (i18n foundation and web e2e), #91 (session and API auth) and #25 (screens). The ADR-025 file prefix in the closed log is taken, so this file uses `25a`. Part A (#90) wrote decisions 1 to 5, part B (#91) adds 6 to 8, and part C appends its own.
**Decision:** (1) The split into #90, #91 and #25 is approved by Merna. (2) URLs: Arabic is the default and has no prefix (`/sign-in`), English lives under `/en` (`/en/sign-in`), `localePrefix: "as-needed"`. The ADR-72 redirect `/sign-in?next=` keeps working. The locale is remembered in the next-intl cookie; #27 later stores it in `profiles.locale`. (3) `app/[locale]/layout.tsx` renders `<html lang dir>` itself and also holds the font and the observability provider; there is no root `app/layout.tsx`, because Next requires the `<html>` element in the root layout and `lang`/`dir` depend on the URL locale. (4) The error-display texts moved from `shared/error-display/messages.ts` (deleted) to `messages/{ar,en}.json` under `errors` (ADR-72 (4)); the home-page exemption from the literal-text rule is removed (ADR-029 (6)). (5) `request.ts` still uses `requestLocale`, which next-intl marks deprecated in favour of the experimental `next/root-params`; the proxy sets it on every request, so the stable API is used until root params leave experimental. (6) Browser Supabase config at runtime (plan decision 3): the project URL, the anon key (public by design, RLS protects the data) and `authGoogleEnabled` travel from the server to the browser through `PublicConfig`, read per request in the locale layout and handed to `AuthProvider`; never `NEXT_PUBLIC_*` (ADR-025), so one build runs in every environment. (7) Role in the token (plan decision 4): the database function `public.custom_access_token_hook` adds the `user_role` claim from `profiles.role` (default `user`) and only `supabase_auth_admin` may run it. The API verifies the token once in `requireAuth` through the `TokenVerifier` port (adapter: `jose` against `<SUPABASE_URL>/auth/v1/.well-known/jwks.json`, issuer and audience `authenticated` checked) and puts `{ userId, role, claims }` in the Hono context; a missing or unknown role claim means `user`; `requireRole("admin")` also lets admins through. A role change reaches the token at its next refresh (1 hour at most). With no `SUPABASE_URL` the verifier rejects everything (fail closed). #29's `withUser` reuses the verified claims. (8) Guard: a pure `decideAccess(pathname, search, signedIn)` is called by `proxy.ts` after the session refresh; a signed-out visitor inside `(dashboard)` goes to `/sign-in?next=<path>`, a signed-in user on `/sign-in` or `/sign-up` goes to `/dashboard`, and `sanitizeNext` accepts only same-site paths. `app/[locale]/(dashboard)/layout.tsx` checks the session again on the server. Supabase error codes map to catalogue codes in `map-auth-error.ts` (rate limits to `RATE_LIMITED`, lost sessions to `UNAUTHENTICATED`); part C adds the sign-in specific codes.
**Reason:** Arabic is the main audience, so its URLs stay clean; one routing definition feeds the proxy, the request config and the navigation helpers.
**Alternatives:** Always-prefixed URLs (`/ar/...`; breaks the `/sign-in?next=` links already in use); a root layout with `<html>` and a `getLocale()` call (works, but splits `lang`/`dir` from the locale segment that owns them).
