# Plan #24: M1 schema with RLS and seed users

Issue: #24 · plan:opus · build:sonnet · Milestone: M1 - Accounts & data · size:M

Depends on #23 (closed, ADR-035). Merna's comment on the issue (`size_charts.owner_id`) is part of this plan.

## Approach

One migration set, one pgTAP test file, one seed. Only SQL, no application code (the repositories come with #29). Every rule that protects data is enforced by the database, so a bug in the API cannot leak rows.

## Schema (SRS §7)

| Table              | Columns and rules                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `profiles`         | `id uuid pk references auth.users on delete cascade`, `name`, `phone` (partial unique index where not null), `phone_verified_at`, `locale check in ('ar','en') default 'ar'`, `role check in ('user','admin') default 'user'`, `created_at`. Row created by trigger `on auth.users insert` (security definer, fixed `search_path`).                                                                        |
| `clients`          | `id`, `owner_id references profiles on delete cascade`, `name`, `notes`, `created_at`; `unique (id, owner_id)`.                                                                                                                                                                                                                                                                                            |
| `measurement_sets` | `id`, `owner_id references profiles on delete cascade`, `client_id` nullable, `label`, `size_label` nullable, `data jsonb check (jsonb_typeof(data)='object')`, `created_at`; composite FK `(client_id, owner_id) references clients(id, owner_id) on delete cascade`, so a set can never point at another user's client. Full shape validation of `data` stays in the application (`measurementsSchema`). |
| `size_charts`      | `id`, `name`, `sizes jsonb check (jsonb_typeof(sizes)='object')`, `is_default`, `owner_id` nullable references profiles on delete cascade (null = system chart, set = a user's private chart, Pro feature after launch, no UI yet), `updated_by`, `updated_at`; partial unique index: one default system chart.                                                                                            |
| `admin_audit`      | `id`, `who references auth.users on delete set null`, `action`, `target`, `before jsonb`, `after jsonb`, `at`; append-only.                                                                                                                                                                                                                                                                                |

`is_admin()` is a `security definer` SQL function (`search_path` fixed) reading `profiles.role` for `auth.uid()`, used by policies so they do not recurse into `profiles` RLS.

## RLS and grants

- `clients`, `measurement_sets`: owner-only for select/insert/update/delete (`owner_id = auth.uid()`); `owner_id` defaults to `auth.uid()`.
- `profiles`: select and update own row only. Column grants: `update` allowed on `name`, `locale` only, so `role` and `phone_verified_at` cannot be changed from the client (only the service role / security-definer functions change them). Insert only through the trigger. No delete policy (deleting the auth user cascades).
- `size_charts`: everyone (including anon) reads system charts; a user reads and writes only rows with `owner_id = auth.uid()`; only an admin writes system charts (`owner_id is null`).
- `admin_audit`: admin select and insert only; no update or delete.
- API login role `api_app` (ADR-035): `login`, `nobypassrls`, no table privileges of its own, `grant authenticated to api_app`. Password: set in `supabase/roles.sql` for local use; on staging it is set once from a CI secret, never in a migration.
- All tables: RLS enabled in the same migration that creates them (rule in `.claude/rules/backend/database.md`).

## Tests

pgTAP, run in CI with `supabase test db` (free, ships with the CLI, needs no app code):

1. User A inserts a client; user B selects it: zero rows; B updates and deletes it: zero rows affected.
2. A tries `insert into clients (owner_id) values (B)`: rejected by `with check`.
3. A creates a set pointing at B's client: rejected by the composite FK.
4. A updates own `profiles.role` to `admin` and `phone_verified_at`: rejected (permission denied on column).
5. A updates `name` and `locale`: allowed; invalid locale rejected.
6. Anon reads system size charts: allowed; anon reads clients: zero rows; a normal user inserts or updates a system chart: rejected; admin does it: allowed; a user writes only their own private chart and cannot read another user's private chart.
7. `admin_audit`: normal user cannot select; admin inserts but cannot update or delete.
8. Signing up creates the profile row (insert into `auth.users`, check `profiles`).
9. Deleting an `auth.users` row removes profile, clients, measurement sets and private charts, and keeps `admin_audit` rows with `who` null.
10. Role `api_app` selects from `clients` without `set local role`: permission denied (guard from ADR-035).
11. Phone unique: two profiles with the same phone rejected; many nulls allowed.

Manual test cases (draft IDs): TC-DB-24-01 seed users can sign in locally; TC-DB-24-02 `db:reset` on a clean database; TC-DB-24-03 migrations apply on staging after merge; TC-DB-24-04..07 map to the pgTAP groups above.

## Decisions (written by the build as `docs/decisions/24-m1-schema.md`)

1. RLS is tested with pgTAP inside the database, not with Vitest (no app code exists yet, it is the CLI's built-in tool).
2. `profiles.role` and `phone_verified_at` are protected by column grants, not by trusting the API.
3. The ADR-035 follow-ups are split: the `api_app` role migration lands here; `DATABASE_URL`, the Drizzle schema mirror and the first repository land in #29 (the brief said all three belong to #24, but #24 has no application code). The M1 brief line is corrected.
4. Seed accounts reuse the names in `seed-data.md`; the issue's `user@` and `workshop@` become `trial@` and `pro@`.
5. A measurement set is tied to its client's owner by a composite foreign key.

## Risks

- A wrong policy leaks client data: the pgTAP matrix above is the safety net and must fail first on a deliberately broken policy (shown in the PR, not committed).
- The auth trigger depends on Supabase's `auth` schema; checked on a fresh local database and on staging through CI.
- `supabase test db` needs Docker in CI (already used by `db-reset`).
- The staging password of `api_app` is a new secret (free, no new service); Merna adds it when #29 needs it.
